# Test vectors for MOR's core

Published test vectors for every layer of MOR's core: the pieces every act is made of, signatures, and verdict vectors (complete acts with the verdict each must get, and the rule that decides it). An implementation of the eight texts in `spec/` should reproduce every value here.

**Stand-ins until the freeze.** The six MIR hashes the acts name (`IDENTITY`, `ENVELOPES`, `TEXT`, `MONEY`, `AGREEMENTS`, `DEVELOPMENT`) are fixed only at the freeze, from the frozen texts (Development rule 26). Until then every vector uses stand-ins, SHA-256 of a label, listed in each file that uses them (`verdicts.json`, `"mirs"`). At the freeze the files are generated again with the real hashes; every act id changes, no verdict does.

**Test data.** Every key, seed and secret here is derived from a label and is test data, labelled so. None may be used for anything else.

All byte strings are lowercase hexadecimal.

## The files

| `sealed.json` | A sealed container, `[to, locked-act]`, every input fixed, and what the recipient opens. | Envelopes, "Sealed container" |
| `signatures.json` | Schnorr over secp256k1 (BIP-340, scheme 1): the key from a fixed secret, the act id signed, signatures with a given and a zero `aux`, and nine signatures that must fail, one reason each. **Size.** `verdicts.json` is about 1.45 MB (1,446,287 bytes), most of it SLH-DSA-SHA2-128f chain signatures (17,088 bytes each), each held once in the pool and named by every case that needs it.

## The verdict vectors

Each case in `verdicts.json` names the acts a verifier holds (complete bytes, in the pool), the facts that are not acts (inclusion proofs a home served; anchors the verifier checked; the rail's answers for a receipt or claim, that it is valid and which payment its proof is, which the core never reads itself; a private act's content key, as its recipient holds it; where a private act was found), a question and its verdict. The questions are explained in the file's `about`. Every act is public save one private link claim, whose key is stated as a fact.

**What no vector covers**, and why: proofs of a home's log handed to a verifier beyond the audit case; a private act beyond the link claim (a private act's opening is `open-act.json`); succession plans, issuance and the owners' matters (their acts are long chains of chain signatures, megabytes of SLH-DSA signatures); a rail's own proof (a rail Module's, outside the core); anchors as proofs (an anchoring cMIP's: the vectors state the anchor as a checked fact).

The act id does not depend on the signature, so every id here is final for its outside.

## What changed since the previous edition

For a verifier built against the previous edition of these vectors, each change, so that a known change can be told from a divergence:
- `canonical-text.json`: rules are numbered as Text numbers them, 7 to 12 (they were 1 to 6), and where a string breaks several, the rule given is the first in the order numbered, each rule checked over the whole string (Text rule 13); two cases test that order.
- `cbor.json`: a NaN whose payload needs single width, accepted as a single and refused as a double.
- `open-act.json` and `verdicts.json`: a new content key and nonce for every act (Envelopes rule 9); every act id changed, no earlier verdict did, save as listed here.
- `verdicts.json`: each inclusion proof names the receipt it proves; the keepers' rule in a deadline question is written as the format writes it, `[0]`; the payment-to-oneself case is labelled for what it is; new facts (`rail_payments`, the rail's answer of which payment a proof is; `content_keys`; `found_at_home`); "paid toward" and "disagreements" may answer `unknown`; the status word "not counting" (Identity, "Which rotation counts"); a "succession" question; the MIR hash is over the file's text less one final line break and nothing else, so the draft's status line case now keeps that line (Development rule 26); the cases listed above as new.
- This edition adds: a rotation whose one kept tip does not fit its line now stands (valid), its tip keeping nothing (void), where the previous answer was invalid (Identity, rotation check 7); the chain question's stop reasons read "genesis unknown" and "genesis invalid"; answers that depend on whether two receipts or claims whose payment the rail's answer does not name are one payment are unknown, and only those (a vow's sale, the status word "unknown" for a sale, a vow's `unknown` list, and "refund repaid"), with vectors on both sides of each; and the heavy rules, on acts holding chain signatures: a collective's closing and its fork (each complete, and not with one member's chain signature not held), an act of the collective before and after each, an agreement as a party of another, and a chain of judgment (the judge's settlement, the next link waiting while the judge's period runs, settling once it has passed, the judge's late answer counting for nothing). New questions: "vow", "refund repaid", "closing", "fork", "version in force"; new facts: `judges_lapsed`, `settled_out_of_turn`. An answer that depends on one such pair is judged both ways and stands where both agree; one that depends on two or more is unknown: so the vow confirmed by a later claim, without the rail's answer, now answers unknown (Money rule 12).
